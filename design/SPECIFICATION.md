# Техническое задание · Маяк

Версия 1.0 · 26 сентября 2026. Статус: проектное ТЗ. Включает подтверждённые заметки, задачи и перенос файлов; платформы и предлагаемые лимиты ниже — рабочие допущения для первой реализации. Выбор аккаунтов, региона и тарифа остаётся за владельцем. Этот документ не означает, что инфраструктура уже создана.

## 1. Назначение и результат

Разработать личное приложение с работой без интернета и синхронизацией между Windows, macOS, Linux, iOS, Android и браузером. Пользователь создаёт заметку, отмечает задачи, прикрепляет файл и продолжает работу на другом устройстве под тем же аккаунтом. При обрыве связи приложение сохраняет данные локально и продолжает обмен после восстановления сети. При конкурирующих изменениях не допускается тихая потеря одной из версий.

Первая поставка: веб/PWA и настольные клиенты; затем мобильные сборки на общем ядре. Если все шесть платформ обязательны в день запуска, этап мобильной адаптации входит в критерии релиза, а не объявляется готовым заранее. Нижняя граница поддерживаемых версий ОС фиксируется после проверки актуальной матрицы выбранного runtime; тестирование проводят на реальных ОС, а не только в режиме эмуляции браузера.

### Что входит

- Личный аккаунт, вход, выход, список устройств и отзыв сессии.
- Текст и Markdown, заголовок, теги, закрепление, поиск.
- Чек-листы внутри заметок и общий обзор задач.
- Локальная база и очередь отправки, инкрементальная синхронизация.
- История, корзина, восстановление и экспорт.
- Вложения, самостоятельные файлы, скачивание для офлайн-доступа.
- Передача независимой копии файла одному из своих устройств через облако.
- Светлая/тёмная тема, клавиатура, адаптивная компоновка, русский интерфейс.

### За пределами первой версии

Публичные ссылки, командное редактирование, организациями управляемые аккаунты, AI-функции, OCR, расшифровка аудио, полная синхронизация папок ОС, прямой P2P/LAN-обмен, изменение двоичных файлов внутри приложения, сквозное шифрование. Последнее можно включить только отдельным этапом с управлением ключами и пересмотром поиска/экспорта/восстановления. Не использовать в продукте заявление «сервер не может прочитать заметки», пока E2EE не реализовано и не проверено.

## 2. Архитектура и место хранения

### Рекомендуемый облачный вариант

| Слой | Предлагаемое решение | Какие данные хранятся |
|---|---|---|
| Веб-интерфейс и HTTPS API | Vercel | Сборка клиента, обработчики запросов; не постоянные пользовательские файлы на локальном диске функции |
| PostgreSQL | Supabase, подключённый к проекту Vercel; альтернатива Neon | Аккаунты приложения, заметки, версии, метаданные файлов, устройства, очередь передач, журнал изменений |
| Авторизация | Supabase Auth при выборе Supabase | Идентичности, сессии и подтверждение входа |
| Файлы | Приватное хранилище Vercel Blob | Содержимое вложений и самостоятельных файлов, версии объектов |
| Native-клиенты | SQLite в каталоге данных приложения | Документы, локальный индекс, outbox, последняя серверная ревизия |
| Веб/PWA | IndexedDB, Cache Storage для оболочки | Локальные документы, очередь, выбранные офлайн-файлы в пределах квоты браузера |
| Файлы на устройстве | Управляемый каталог приложения; в Web — браузерное хранилище | Загруженные и закреплённые для офлайн-доступа копии |
| Резервные копии | Отдельная политика DB + копия объектов в независимом bucket | Восстанавливаемый согласованный набор базы и файлов |

Vercel подключает внешние Postgres-базы через Marketplace. Прежний Vercel Postgres больше не предлагается; база физически находится у выбранного провайдера. Это не запуск PostgreSQL внутри serverless-функции. Источник: [Vercel Postgres](https://vercel.com/docs/postgres).

Для пользовательских файлов выбрать private Blob store. Приватность хранилища не заменяет авторизацию отдельного пользователя в API: перед каждой выдачей файла проверить owner_id. В соответствии с текущей документацией приватные объекты читаются через серверный `get()` и выдаются через Function. Не предполагать, что закрытый объект имеет публичный URL для прямого скачивания. Источник: [Vercel Blob](https://vercel.com/docs/vercel-blob).

Схема обмена:

```text
Клиент: редактор → локальная БД + outbox (одна транзакция)
                       ↓ HTTPS /sync/push
                  API на Vercel
                       ↓ проверка пользователя и ревизии
                  PostgreSQL провайдера
                       ↑ /sync/pull?cursor=...
Другой клиент: локальная БД → обновление списка и редактора

Файл: клиент → авторизованная загрузка в private Blob
                 ↓ подтверждение завершения
             метаданные в PostgreSQL → уведомление других устройств
Получатель → авторизованный API чтения → поток private Blob → локальная копия
```

База, функции и Blob по возможности располагаются в близких регионах. Регион базы, хранилища и резервных копий выбирается явно, фиксируется в конфигурации окружения и документации. До выбора нельзя обещать конкретную страну хранения. Трафик, реплики и резервные копии проверяются по договору провайдера отдельно от основного региона.

### Стек

- TypeScript + React; Vite для общего клиентского пакета, отдельные HTTP handlers на Vercel. Не требовать SSR для личного офлайн-редактора.
- Tauri 2 для настольной оболочки; мобильная оболочка на Tauri 2 после проверки ввода, файлов и lifecycle. Общие доменные типы, sync core и дизайн-токены. Возможность Tauri работать с desktop/mobile описана в [официальной документации](https://v2.tauri.app/); конкретные плагины проверяются на каждой платформе.
- SQLite для native и IndexedDB для Web за интерфейсом LocalStore. Не считать localStorage надёжной базой.
- PostgreSQL, SQL-миграции, pooled server-side connection, API runtime Node.js. Не открывать клиенту административное подключение к базе.
- Markdown-редактор с экранированным/санитизированным preview. В первой версии допускается plain-text source + preview. Выбор редакторской библиотеки — ADR с проверкой IME и мобильной клавиатуры.
- Начальная синхронизация через push/pull HTTPS. Polling активного приложения с интервалом 2–5 секунд плюс немедленный pull при focus/reconnect; idle-backoff до 30–60 секунд. После push инициировать pull. Background в мобильных ОС — best effort: синхронизация при следующем открытии гарантируется, постоянная фоновая работа не обещается.
- Realtime transport — возможная оптимизация, а не источник истины. Потерянное уведомление всегда компенсируется pull по курсору. Поддержку и ограничения выбранного транспорта на Vercel проверить перед реализацией; не опираться на предположение о бессрочном процессе.

### Альтернатива с собственным сервером

Postgres + S3-совместимое хранилище + тот же HTTP API на VPS/NAS. Внутренние интерфейсы AuthProvider, ObjectStore, LocalStore и SyncTransport не зависят от конкретного vendor API. Vercel Blob не объявлять S3-совместимым: для него реализовать собственный адаптер. Миграция включает экспорт SQL/JSON, потоковое копирование объектов, сверку контрольных сумм и переключение endpoint.

## 3. Сущности и модель данных

Все идентификаторы UUID генерируются на клиенте там, где нужен offline-create. owner_id назначается сервером из проверенной сессии, а не принимается из тела запроса. Время клиента — информационное; порядок принятия определяется серверной последовательностью.

| Сущность | Основные поля | Ограничения |
|---|---|---|
| users | id, auth_subject, created_at, locale, quota_bytes | auth_subject unique |
| devices | id, owner_id, name, platform, last_seen_at, revoked_at | Устройство принадлежит одному аккаунту |
| notes | id, owner_id, title, document JSONB, tags, pinned, revision, deleted_at, created_at, updated_at | (owner_id,id) индекс, revision растёт на сервере |
| note_versions | id, note_id, owner_id, revision, snapshot, created_at, source_device_id | (note_id,revision) unique |
| changes | owner_id, seq, entity_type, entity_id, revision, operation, payload | (owner_id,seq) unique, последовательность без пропуска коммитов |
| sync_heads | owner_id, last_seq | Блокировка строки на время записи batch |
| mutations | owner_id, mutation_id, request_hash, result, created_at | Идемпотентность повторных запросов |
| files | id, owner_id, display_name, mime, size_bytes, object_key, checksum, revision, status, deleted_at | object_key immutable, статус ready только после завершения |
| attachments | owner_id, note_id, file_id | Проверять общую принадлежность; связи не дают дополнительных прав |
| upload_sessions | id, owner_id, file_id, provider_upload_id, completed_parts, reserved_bytes, expires_at | Не помещать постоянные секреты провайдера в клиент |
| transfers | id, owner_id, file_id, file_revision, target_device_id, state, expires_at, received_at | Передаётся конкретная неизменяемая версия |
| device_cursors | owner_id, device_id, last_ack_seq, updated_at | Для диагностики; не путать с доказательством получения файла |

Локально дополнительно: outbox(mutation_id, entity_id, base_revision, snapshot, state, retry_at), sync_cursor, pending_conflicts, local_file_paths, download_jobs, search_index. Данные разных аккаунтов разделять отдельными пространствами/БД; при смене аккаунта не показывать предыдущий cache.

### Документ и задачи

Каноническая заметка — структурированный документ с блоками `{id, type, text, checked?, fileId?}`. Типы v1: markdown, task, attachment. У каждого блока стабильный UUID. Заголовок хранится отдельно. Чекбокс обновляет исходный task-блок заметки; общий список задач — производная проекция, а не вторая независимая копия. Экспорт в Markdown преобразует task в `- [ ]` или `- [x]`. При обратном импорте создаются новые UUID, если не используется собственный JSON-архив. При смене представления редактора сохранять существующие блоки и их id; не пересоздавать весь документ на каждый keypress.

В MVP note revision охватывает документ целиком: конкурентное изменение разных задач одной заметки может вызвать конфликт. Это осознанный компромисс ради надёжности. CRDT/Yjs — отдельный последующий ADR и миграция; не обещать автоматическое бесконфликтное слияние в первой версии.

## 4. Синхронизация и конфликты

### Локальное сохранение

Редактор применяет изменение сразу. Пакет изменений попадает в LocalStore и outbox атомарно; только после commit UI показывает «Сохранено на устройстве». Использовать короткое объединение операций до 150 мс и принудительную запись при blur/navigation/background, но не полагаться только на unload. При ошибке локальной записи показать постоянное предупреждение и экспорт текста; не выдавать ложный saved-статус. Цель — отсутствие потери подтверждённых локальных транзакций при аварийном закрытии.

### Отправка

1. Для объекта есть максимум одна отправляемая мутация. Следующие изменения остаются локальными и ждут подтверждения предыдущей ревизии.
2. Push содержит mutationId, entityId, baseRevision, operation и snapshot. До отправки проверить схему и лимиты; сервер проверяет их повторно.
3. Сервер проверяет сессию, отозванное устройство, owner и idempotency key. Повтор с тем же ключом и телом возвращает прежний результат; с другим телом — ошибку.
4. В транзакции сервер блокирует sync_heads конкретного владельца, проверяет baseRevision, увеличивает revision и seq, сохраняет snapshot/history/change и результат мутации. Ответ возвращается после commit.
5. Клиент атомарно отмечает outbox ack, обновляет baseRevision и затем готовит следующую мутацию. Сбой между commit сервера и получением ответа покрывается идемпотентностью.

Почему нужен sync_heads: простой глобальный sequence может выдать номер транзакции, которая коммитится позже уже полученного курсора. Сериализация записей одного владельца исключает пропуск изменения из-за перестановки коммитов. Это допустимый MVP-компромисс для личных аккаунтов; нагрузку проверить отдельно.

### Получение

Pull возвращает события после opaque cursor, максимум 200 за страницу, hasMore и nextCursor. Cursor привязан к аккаунту, версии протокола и snapshot epoch. Применение страницы и продвижение курсора — одна локальная транзакция. Если по объекту есть несинхронизированные изменения, серверный snapshot не перезаписывает их: сохранить для сравнения, а локальный outbox оставить.

При первом запуске сервер выдаёт согласованный snapshot с high-water cursor и последующие изменения. При слишком старом курсоре — `410 CURSOR_EXPIRED`: экспорт/сохранение pending outbox, полная загрузка серверной базы во временное локальное пространство, повторное согласование pending операций и атомарное переключение. Не удалять pending-данные ради resync.

### Конфликт

Если baseRevision не совпадает, вернуть `409 REVISION_CONFLICT` с серверной ревизией и snapshot. Клиент сохраняет обе версии и показывает сравнение: «Моя версия», «С другого устройства», «Сохранить обе». Последнее создаёт отдельную заметку с новым id и пометкой происхождения; оригинал обновляется серверной версией после сохранения копии. Выбор одной версии создаёт новую мутацию на базе актуальной ревизии, не удаляет историю. Повторный конфликт снова обрабатывается явно.

Конкурентное удаление и изменение: удаление не уничтожает локальную правку; предложить восстановить как новую заметку. Нет политики «последний клиент по часам выигрывает». Смещение часов устройства не должно влиять на результат.

### Удаление, история и сроки

- Корзина: 30 дней — проектный default, настраиваемый сервером.
- История: хранить принятые версии минимум 30 дней; частоту snapshot можно оптимизировать, сохраняя заявленную возможность восстановления. Восстановление создаёт новую текущую ревизию.
- Tombstones/change log: минимум 90 дней; клиент с более старым курсором проходит полную ресинхронизацию. UUID удалённых объектов нельзя повторно использовать для create. Purged-id registry или generation epoch предотвращает воскрешение старой записи.
- Идемпотентные результаты: 90 дней; для старых pending операций client сначала сверяет состояние и выполняет resync, а не слепой повтор.
- Удаление последней связи заметки с файлом не удаляет самостоятельный объект без согласованной политики. Физическая очистка Blob запускается лишь после окончания восстановления и отсутствия ссылок/передач.
- Очистка корзины и удаление аккаунта требуют явного подтверждения в продукте; доступ отзывается немедленно, фоновые задачи удаляют объекты с повторениями и аудитом без содержимого.

### Повторы

Retry с exponential backoff и jitter: 1, 2, 4, 8 секунд, далее до 60 секунд; учитывать Retry-After. 401 — обновить сессию или запросить вход, не удаляя outbox. 403 — остановить операцию и показать причину. 409 — конфликт. 413 — слишком большой объект. 429 — отложить. 5xx/timeout — повтор с тем же mutationId. Внутренние ошибки не показывают токены и SQL.

## 5. Файлы и перенос

### Продуктовые лимиты для оценки

Стартовые допущения: до 100 MiB на файл, до 2 GiB на аккаунт, 10 000 заметок, до 1 MiB сериализованного документа заметки, до 10 активных устройств. Это ограничения продукта для первой реализации, а не утверждение о лимитах Vercel. Перед запуском сопоставить с действующим тарифом и скорректировать. В UI единицы размера использовать последовательно; в API все размеры в байтах.

### Загрузка

1. Пользователь выбирает файл, drag-and-drop или системное «Поделиться». При offline файл копируется в локальную очередь, если хватает места; иначе понятная ошибка без ложного успеха.
2. API создаёт upload session, атомарно резервирует квоту и возвращает короткоживущее разрешение только на допустимый объект/размер. Не выдавать read-write токен всего Blob store клиенту.
3. Клиент отправляет тело в Blob через поддерживаемую авторизованную client-upload схему. Большое тело не помещать в обычный JSON POST через API приложения.
4. Для multipart сохранять uploadId, номера частей, etag и привязку к исходному файлу. После reconnect повторять только неподтверждённые части. После перезапуска браузер может попросить повторно выбрать исходный файл; проверить размер и checksum перед продолжением.
5. Сервер проверяет завершение, принадлежность объекта, фактический размер, доступную квоту и контрольную сумму по согласованному механизму. ETag не объявлять SHA-256, особенно для multipart. Для проверки SHA-256 крупного объекта нужен потоковый валидатор/фоновая задача, а не неограниченная работа в коротком запросе.
6. Только после проверки объект получает ready и попадает в журнал синхронизации. Брошенные upload sessions освобождают резерв по TTL и очищаются фоновой задачей.

Vercel Blob SDK документирует multipart и повтор неудачных частей: [SDK](https://vercel.com/docs/vercel-blob/using-blob-sdk). Возобновление после закрытия процесса — отдельная задача приложения, не автоматическая гарантия флага multipart. В этапе 1 сделать обязательный технический прототип для private client upload, persist/resume и потокового чтения. Если выбранный SDK/план не обеспечивает требуемый сценарий, реализовать ObjectStore на S3-совместимом сервисе с возобновлением; не скрывать ограничение.

### Получение и локальное хранение

Список файлов содержит metadata без загрузки байтов. Заметки и задачи скачиваются автоматически; файлы — по запросу, с отдельной отметкой «Доступен офлайн». Закреплённые файлы не вытесняются обычной очисткой cache. Сначала записывать временный файл, сверять размер/checksum и только затем атомарно переименовывать. Range/resume скачивания проверить в адаптере; при неподдерживаемом диапазоне явно перезапустить загрузку, не склеивать несовместимые данные.

Для private Blob API проверяет сессию и owner, читает `get()` и стримит ответ с корректным Content-Disposition и безопасным именем. Browser cache — приватный, политика зависит от режима офлайн; публичный CDN-ответ с пользовательским файлом недопустим. Объекты immutable: новая версия получает новый object_key, чтобы кэш не выдавал старое содержимое.

Разрешить документы, изображения и архивы как двоичные объекты; не выполнять их и не рендерить произвольный HTML/SVG в доверенном origin. Предпросмотр v1 ограничить безопасными типами, остальные — скачать. Проверять пути, Unicode-имена, зарезервированные имена Windows и обход каталога. Текст заметки не использовать как путь файла.

### «Передать копию»

Передача адресована своему зарегистрированному устройству и конкретной версии файла. Создаётся transfer со сроком 7 дней. Отправитель видит queued → available → received; статус received приходит только после checksum/commit на получателе. Offline-получатель получает задание при следующем открытии. Повтор получения идемпотентен по transfer id. Передача не означает автоматическое исполнение или открытие файла.

На desktop можно сохранять в выбранную пользователем папку после разрешения ОС; на мобильных — сначала в sandbox, затем экспортировать через системный диалог. В браузере пользователь подтверждает скачивание; приложение не обещает молча записать файл в произвольный каталог. Отзыв устройства закрывает его будущий доступ, но не удаляет уже экспортированные копии.

Отмена до получения удаляет задание, но не исходный файл. Истечение TTL удаляет временную ссылку передачи; общий файл остаётся согласно политике хранения. Загрузка новой версии не меняет уже отправленную копию. Это облачная передача, не аналог AirDrop и не синхронизация всей папки.

## 6. Контракты API

Все маршруты `/api/v1`, HTTPS, JSON кроме бинарной выдачи; даты ISO 8601 UTC. Схемы валидируются общей библиотекой на сервере, версия protocolVersion обязательна. Поддержать совместимость текущего и предыдущего клиента либо вернуть понятный upgrade-required без потери локальных данных.

| Метод и путь | Вход | Выход / особенности |
|---|---|---|
| GET /bootstrap | protocolVersion, deviceId | Снимок аккаунта, лимиты, snapshot cursor |
| POST /sync/push | deviceId, mutations[] | Для каждой мутации ack/revision/seq или conflict; максимум 50, общий размер запроса ограничен |
| GET /sync/pull | cursor, limit | changes[], nextCursor, hasMore |
| GET /notes/:id/history | before, limit | История только своего объекта |
| POST /notes/:id/restore | versionId, baseRevision, mutationId | Новая ревизия; конфликт обрабатывается обычно |
| POST /files/uploads | name, sizeBytes, mime, checksum | uploadId, срок, разрешённый метод загрузки |
| POST /files/uploads/:id/complete | parts / подтверждение | pending-verification или ready; проверяет сервер |
| DELETE /files/uploads/:id | idempotency key | Отмена и освобождение резерва |
| GET /files/:id/content | version, optional Range | Авторизованный поток, Content-Disposition |
| POST /transfers | fileId, fileRevision, targetDeviceId, mutationId | id, state, expiresAt |
| POST /transfers/:id/received | checksum, deviceId, mutationId | received после проверки получателя |
| GET /devices | — | Список устройств владельца |
| DELETE /devices/:id/session | подтверждение | Отзыв сессии на сервере |
| POST /exports | format, includeFiles | jobId; готовый архив выдаётся только владельцу |
| DELETE /account | повторное подтверждение личности | Отзыв доступа и идентификатор удаления |

Пример push:

```json
{
  "protocolVersion": 1,
  "deviceId": "UUID устройства",
  "mutations": [{
    "mutationId": "UUID операции",
    "entity": "note",
    "entityId": "UUID заметки",
    "baseRevision": 7,
    "operation": "upsert",
    "document": {
      "title": "Планы на осень",
      "blocks": [{"id":"UUID блока","type":"task","text":"Отправить материалы","checked":false}],
      "tags": ["Личное"],
      "pinned": false
    }
  }]
}
```

В production UUID-строки должны быть валидными UUID; пример описательный. Ошибка: `{code, message, retryable, requestId, details?}`. requestId пригоден для диагностики, но не содержит персональные данные. Проверка ownership обязательна и для id в теле, и для вложенных fileId, и для history/transfer/export, а не только для верхнего пути.

## 7. Авторизация и защита

Вход по email с подтверждением через выбранного Auth-провайдера. На Web сессия по защищённой cookie (HttpOnly, Secure, SameSite), CSRF-защита для state-changing endpoints. Native — OAuth/PKCE-сценарий провайдера и хранение refresh token в системном защищённом хранилище, не в открытом файле настроек. Проверять issuer/audience/expiry и статус сессии. Управление устройством связывается с реальной сессией, одного deviceId недостаточно для аутентификации.

Каждый запрос выполняет проверку владельца; Row Level Security в Postgres — дополнительная защита при соответствующей модели подключения. Административный ключ и Blob credentials остаются на сервере. Не надеяться на RLS при использовании роли, которая его обходит: application authorization остаётся обязательной. Секреты в Vercel environment, отдельные для preview/staging/production.

TLS в передаче; шифрование дисков/хранилища на стороне провайдера проверяется при выборе конфигурации. Это не E2EE. Локальная защита — sandbox ОС и защита диска пользователя; дополнительное шифрование локальной БД требует отдельного ключевого дизайна. Не объявлять SQLite зашифрованным по умолчанию. На Web защищаться от XSS: строгая CSP, sanitization Markdown, отсутствие небезопасного raw HTML, запрет выполнения вложений в основном origin.

Не логировать содержимое заметок, имена личных файлов, токены, адреса скачивания. Метрики — время, байты, результат, request id. Rate limiting входа, sync и выдачи upload grants. Политика приватности должна честно раскрывать провайдеров, регионы, сроки резервного хранения и наличие/отсутствие E2EE.

При выходе предупредить о pending изменениях, дать синхронизацию/экспорт и выбор очистки локального cache. Не удалять единственную несинхронизированную копию автоматически. При отзыве сессии удалять токен, останавливать сетевые операции; сохранённые данные обрабатывать по заранее согласованной политике устройства.

## 8. Нефункциональные требования

Проектные цели, подлежащие измерению, а не гарантии облачного тарифа:

| Метрика | Цель | Условия измерения |
|---|---|---|
| Локальное подтверждение записи | p95 ≤ 250 мс | Документ до 100 KiB, диск без ошибки |
| Реакция ввода | Не блокировать основной поток > 50 мс | Обычный набор текста, индекс обновляется вне критического пути |
| Поиск | p95 ≤ 150 мс | 10 000 заметок среднего размера 2 KiB после индексации |
| Между активными устройствами | p95 ≤ 5 с после server ack | RTT ≤ 150 мс, оба клиента foreground, интервал polling 2 с |
| Открытие локальной заметки | p95 ≤ 200 мс | База прогрета, документ до 100 KiB |
| Запуск тёплого приложения | ≤ 2 с | Согласованный эталонный Windows/Android девайс |
| Потеря подтверждённых локальных данных | 0 в crash-suite | Принудительное закрытие после local commit |
| Восстановление из backup | RPO ≤ 24 ч, RTO ≤ 8 ч | После выбора тарифа и проверки restore drill |

Зафиксировать эталонные устройства и версии клиентов в test plan. Виртуализировать длинный список, не передавать целую библиотеку на каждый keypress, ограничивать batch размер. Контролировать расходы на polling: при росте нагрузки перейти к уведомлениям + pull без изменения контракта данных.

Работа offline не означает неограниченную гарантию хранения в браузере: квоты и очистка site data зависят от браузера/ОС. Запрашивать persistent storage где поддерживается, показывать состояние и предлагать экспорт; native-клиент предпочтителен для надёжного длительного офлайн-хранения.

## 9. Резервирование и эксплуатация

Определить DB backups/PITR согласно выбранному тарифу; не считать бесплатный план автоматически резервируемым. Для Blob отдельно организовать независимую копию объектов и manifest со связями/версиями/checksum. Копия БД без файлов — неполная резервная копия приложения. Перед удалением старых объектов убедиться, что это не нарушает окно восстановления.

Ежедневная резервная копия, срок 30 дней как исходная политика. Ежемесячное тестовое восстановление в изолированное окружение: заметки, задачи, файлы и права доступа. Удалённые пользовательские данные могут сохраняться в backups до окончания объявленного срока; это раскрывается в интерфейсе удаления и политике приватности.

Метрики: sync lag, conflict rate, размер outbox, количество retries, частота ошибок локальной записи, upload completion rate, storage bytes и egress. Alert: рост 5xx, очередь зависших upload sessions, переполнение квоты, ошибка резервирования. Production и staging раздельные DB/Blob stores; preview deployments не получают production-права по умолчанию.

Расходы = тариф Vercel + вычисления/запросы + PostgreSQL + хранимые GB + загрузки/скачивания и исходящий трафик + резервные копии + отправка auth-писем. Для приватного Blob учитывать путь выдачи через Function по действующей тарификации. Не обещать бесплатную эксплуатацию без оценки числа пользователей, общего объёма файлов и месячных скачиваний.

## 10. Экспорт и импорт

Экспорт Markdown для заметок и задач; JSON-архив для полной структуры, тегов, UUID и связей; ZIP с файлами и manifest. Большой экспорт — фоновая задача с прогрессом и сроком доступности, не один неограниченный HTTP handler. До скачивания проверять владельца. Импорт TXT/MD/собственного JSON: dry-run с количеством записей, проверка размеров и формата, новый namespace UUID или сопоставление по manifest; повтор одного архива не создаёт дубликаты без предупреждения. Прямой импорт формата Simplenote добавить только после проверки реального экспортного файла и его схемы; не объявлять совместимость заранее.

## 12. Этапы и критерий готовности

1. Технический прототип: локальный commit/outbox, два клиента, конфликт, private upload/resume/download. Решить риски runtime и хранилища до полировки UI.
2. Основной клиент: заметки, задачи, поиск, история, корзина, auth, светлая/тёмная тема выбранного направления.
3. Файлы и устройства: квота, перенос копии, offline pin, восстановление после сети, отзыв сессии.
4. Платформы: сборки Windows/macOS/Linux, мобильные lifecycle, клавиатура, системные share/save; Web PWA cache и ограничения браузеров.
5. Подготовка релиза: миграции, мониторинг, restore drill, документация, проверка доступности и signed builds.

На выходе: исходники monorepo, README локального запуска, env.example без секретов, SQL-миграции, API schema, дизайн-токены, каталог компонентов, тесты sync/file/security, протокол приёмки и артефакты сборок. Не ставить «готово» на основании только работающего интерфейса. Подписание нативных сборок и публикация требуют аккаунтов владельца. Конкретный срок оценивается после технического прототипа и уточнения размера команды.

## Настройки внешнего вида

Подтверждённое требование: пользователь может менять шрифт и тему в разделе «Настройки → Внешний вид» на каждой платформе.

- Темы: «Тихая ясность / Светлая» (по умолчанию), «Тихая ясность / Тёмная», «Как в системе». Тёмная тема использует ту же структуру и семантические токены, а не альтернативный дизайн 04. Системный режим реагирует на изменение настроек ОС без перезапуска.
- Шрифт интерфейса и шрифт редактора выбираются независимо: системный, без засечек, с засечками, моноширинный. Все варианты поддерживают кириллицу; fallback обязателен. Для одинакового начертания на всех ОС шрифты поставляются локально после проверки лицензий.
- Размер текста редактора: 14–24 px, шаг 1 px; по умолчанию 17 px. Изменение не меняет содержимое заметок и экспортируемый Markdown.
- Показывать живое превью с заголовком, абзацем, задачей и кнопкой. Применять сразу, без дополнительной кнопки сохранения. Предусмотреть «Сбросить оформление».
- Настройки сохраняются локально и работают без сети. В первой версии они относятся к устройству; синхронизация заметок не должна менять оформление другого устройства.
- При ошибке локального сохранения честно сообщить, что выбор действует только в текущем сеансе. Повреждённые значения заменять безопасными значениями по умолчанию.
- Проверки: перезапуск, переключение системной темы, отсутствие выбранной гарнитуры, кириллица, 320 px, максимальный размер текста, zoom 200%, клавиатура и контраст обеих тем. Выбор шрифта не ломает иконки, диалоги и нижнюю навигацию.

Макет `mayak-settings.html` показывает выбор темы и шрифтов с локальным сохранением. Это отдельный интерактивный экран; он ещё не подключён к остальным демонстрационным экранам.

### Полная настройка шрифта (актуальное уточнение)

Для интерфейса и редактора независимо доступны четыре свойства: **семейство, размер, толщина и цвет**.

- Семейства: системный, Arial / sans-serif, Georgia / serif, Consolas / monospace с платформенными fallback. При отсутствии начертания использовать ближайшее доступное; не обещать идентичную толщину без поставки шрифтов.
- Размер: 14–24 px с шагом 1; по умолчанию интерфейс 16 px, редактор 17 px. Заголовки сохраняют иерархию, масштабирование ОС учитывается.
- Толщина основного текста: 300, 400, 500, 600, 700; по умолчанию 400. Заголовки и смысловое выделение остаются различимыми.
- Цвет: «Цвет из темы» по умолчанию или собственный HEX/RGB через палитру. Пользовательский цвет меняет основной текст выбранной области, но не цвета ошибок, ссылок, кнопок и других семантических состояний.
- Пользовательский цвет сохраняется при смене темы. Проверять контраст с фактическими поверхностями и показывать предупреждение ниже 4.5:1; предложить вернуть цвет темы. Не менять выбранный цвет без действия пользователя.
- Живое превью, локальное сохранение, валидация значений, миграция старых настроек и общий сброс обязательны. Оформление не изменяет текст заметок и экспортируемые файлы.
- Проверить комбинации тем, семейств, крайних размеров и толщин; цвета с низким контрастом; перезагрузку; повреждённое хранилище; системную смену темы; сброс и клавиатурную доступность.

Макет реализует эти настройки в собственном предпросмотре. Подключение к основным экранам приложения остаётся задачей реализации.


## Голосовая диктовка — обязательная функция

### Сценарий и интерфейс

Пользователь может надиктовать текст заметки или пункта задачи вместо ввода с клавиатуры. В редакторе и поле задачи есть доступная кнопка «Диктовать» с иконкой микрофона и текстовой подсказкой. Диктовка вставляет подтверждённый текст в текущую позицию курсора, сохраняя окружающее содержимое и форматирование; нажатие микрофона не удаляет выделенный текст.

Перед началом зафиксировать целевой документ, блок и позицию. При переходе в другую заметку или закрытии редактора остановить сеанс; результат не должен попадать в новый документ. Частичный результат показывать отдельно от подтверждённого текста. Повторные промежуточные и итоговые события не должны дублировать вставку. После остановки вставка допускает обычное редактирование и отмену; уже подтверждённый текст сохраняется локальной транзакцией и синхронизируется как обычная правка.

### Управление и состояния

- Начать / остановить диктовку; повторить после ошибки. Остановка немедленно завершает захват микрофона; финальная обработка обозначается отдельно и может быть отменена.
- Язык диктовки фиксирован: русский (`ru`). Переключателя языка и автоопределения в интерфейсе нет. Речь на других языках не считается поддерживаемым сценарием.
- Состояния: готово, запрос разрешения, слушаю, распознаю, текст вставлен, отменено, нет речи, нет сети, микрофон недоступен, доступ запрещён, язык/движок не поддерживается.
- Во время записи постоянно виден индикатор микрофона и действие остановки. Состояния выражены текстом, а не только цветом. Доступны клавиатура, экранный диктор и крупные зоны касания; не озвучивать через aria-live каждое промежуточное слово.
- При отсутствии поддержки показывать понятное объяснение и сохранять обычный текстовый ввод. Не изображать успешную запись или распознавание заглушкой.

### Платформы и реализация

Обязательный целевой охват: Windows, macOS, Linux, Android, iOS и браузер. Реализовать интерфейс SpeechToTextAdapter с проверкой поддержки русского языка, режима обработки, разрешений, start/stop/cancel, промежуточных и итоговых событий, ошибок и освобождения ресурсов. Системный ввод ОС допустим как дополнительный способ, но не заменяет проверяемую функцию приложения на всех целевых платформах.

До выбора движка проверить официальную документацию и работу в реальных целевых средах: поддержка распознавания не предполагается автоматически из наличия микрофона. Для каждой платформы зафиксировать адаптер, поддержку русского языка, онлайн/офлайн режим и ограничения. Онлайн-распознавание должно иметь явно выбранного провайдера и серверную защиту ключей; не добавлять API-ключи в клиент. Провайдер, стоимость, квоты, длина сеанса и политика обработки аудио фиксируются до подключения сервиса.

Офлайн-диктовка доступна только при подтверждённой поддержке локального движка и установленной модели. Если её нет, объяснить необходимость сети. Не переключаться незаметно с локального распознавания на облачное. Не обещать запись в фоне, после блокировки экрана или закрытия приложения; при прерывании корректно завершить сеанс и сохранить уже подтверждённый текст.

### Приватность и данные

Разрешение микрофона запрашивается после явного нажатия «Диктовать», а не при запуске. До первого облачного сеанса показать поставщика и факт отправки аудио; получить явное согласие на облачную обработку. Отказ не ограничивает обычные заметки. Запись запускается только действием пользователя и прекращается при остановке, отмене, уходе с экрана или закрытии сеанса.

Приложение не хранит исходные аудиозаписи постоянно по умолчанию; временные буферы освобождаются после обработки или отмены. Сроки хранения и использование данных внешним провайдером нужно проверить и раскрыть отдельно, не обещая удаление на его стороне без подтверждения. Сохраняется распознанный текст; аудиозаметки и пересылка записи не входят в эту функцию. Не писать аудио, текст и ключи в диагностические логи.

### Приёмка

Проверить на каждой заявляемой платформе: разрешение и отказ; повторное включение доступа; русскую речь; тишину и шум; отсутствие микрофона; обрыв сети и тайм-аут; остановку и отмену; повторные события; переключение заметки; блокировку/возврат приложения; вставку в середину текста и пункт задачи; отмену вставки; локальное сохранение и дальнейшую синхронизацию. Проверить фактическое прекращение захвата микрофона, отсутствие фоновой записи и утечки ключей. Поддержку платформы объявлять только по результатам проверки, ограничения явно перечислить.

### Статус в дизайн-пакете

Это обязательное требование к реализации. Текущие HTML-макеты и PDF ещё не содержат работающей диктовки; подключённого движка распознавания нет. В финальной версии макетов добавить микрофон и все перечисленные состояния. Голосовые команды управления приложением и запись аудиофайлов — отдельные функции, не подразумеваемые диктовкой.

## Локальный движок распознавания: Whisper tiny и small

Решение владельца: для телефонов использовать многоязычную **Whisper tiny** (`ggml-tiny.bin`), для компьютеров — многоязычную **Whisper small** (`ggml-small.bin`). Версии `.en` не применять. Единственный поддерживаемый язык диктовки — русский; явно устанавливать `ru` при распознавании. Запуск распознавания выполняется локально через `whisper.cpp` на устройстве, без отправки аудио на Vercel или в другие облачные сервисы. Это выбор для прототипирования и измерений, а не утверждение об одинаковой скорости или точности на всех устройствах.

### Поставка и жизненный цикл модели

- Разделять код приложения и файл модели. Первый запуск диктовки предлагает загрузить модель по явному действию пользователя; показывать её приблизительный размер (около 75 MiB), требуемое место и состояние загрузки. Не начинать передачу модели в фоне без выбора пользователя.
- Загружать только из зафиксированного официального источника, закрепить версию `whisper.cpp` и контрольную сумму SHA-256 модели в сборочном манифесте. Проверять сумму до активации. Документировать лицензии движка и весов.
- Хранить модель в файловой области приложения, доступной офлайн, отдельно от синхронизируемых пользовательских файлов. Предусмотреть паузу/повтор загрузки, удаление модели и повторную установку. Модель не загружать в Postgres, Blob или резервные копии пользовательских заметок.
- В настройках показать «Whisper tiny · на этом устройстве», размер и статус установки. Если модель отсутствует, диктовка недоступна до установки; обычный текстовый ввод остаётся доступным.

### Платформенные адаптеры

- Native Windows, macOS и Linux: использовать локальный адаптер `whisper.cpp` с архитектурой и ускорением, подтверждёнными на конкретной ОС. Не блокировать поток интерфейса во время распознавания.
- Android и iOS: отдельные платформенные сборки движка; учитывать ограничение памяти, тепловую нагрузку, разрешение микрофона и остановку при уходе приложения в фон. Поддержку модели и скорость проверить на реальных устройствах.
- Браузер: отдельная оценка WebAssembly/WebGPU. Не утверждать поддержку офлайн-диктовки только потому, что `whisper.cpp` собирается в WebAssembly; нужны проверка памяти, времени загрузки, скорости и работы в основных браузерах. При недостаточной производительности показывать честное ограничение и сохранять текстовый ввод.
- Интерфейс `SpeechToTextAdapter` должен скрывать различия запуска движка, но явно передавать признак готовности, фиксированный язык `ru`, прогресс, ошибку и факт локальной обработки. Не подменять фактическое распознавание таймером или фиктивным текстом.

### Обработка записи

Записывать PCM с необходимой для движка частотой через платформенный аудиоадаптер; ресемплинг и преобразование должны быть проверяемыми. Перед распознаванием использовать определение речи/тишины либо явное ограничение длительности, чтобы не получать текст из шума. Для первой версии ограничить один сеанс 60 секундами и показывать оставшееся время; значение пересмотреть по результатам замеров. При остановке освободить микрофон немедленно. Временные аудиобуферы удалить после завершения или отмены. Итоговый текст вставлять только после подтверждения движком; при переключении заметки старый результат не вставлять.

### Критерии выбора для выпуска

Провести измерения минимум на одном слабом и одном среднем Android, одном поддерживаемом iPhone и по одному устройству Windows, macOS и Linux; браузеры проверять отдельно. Набор записей: русская речь разных дикторов, имена, числа, пунктуация, список задач, тихая и шумная обстановка. Для каждого случая измерять WER/CER по размеченным фразам, время от остановки записи до текста, пиковую память, размер установки, нагрев/расход батареи и случаи галлюцинации на тишине. Целевые пороги утвердить после базовых замеров на реальном корпусе; до этого не обещать качество уровня Wispr Flow. Если выбранная модель не проходит согласованные пороги на своём классе устройств, сохранить интерфейс адаптера и пересмотреть модель отдельным решением.

Источники: [whisper.cpp](https://github.com/ggml-org/whisper.cpp), [модели и языки Whisper](https://github.com/openai/whisper#available-models-and-languages).


## Решение по моделям для разных устройств

Для мобильных устройств выбрана tiny, для настольных — small; обе модели работают с фиксированным языком `ru`.

| Устройство | Модель по умолчанию | Ориентир размера модели | Назначение |
|---|---|---:|---|
| Android и iOS | Whisper **tiny multilingual** (`ggml-tiny.bin`) | около 75 MiB | Локальная диктовка с меньшими требованиями к памяти и энергии |
| Windows, macOS и Linux | Whisper **small multilingual** (`ggml-small.bin`) | около 466 MiB | Локальная диктовка с приоритетом точности на настольном устройстве |
| Браузер | Выбор после испытаний; не обещать автоматическую установку small | зависит от среды | Отдельно проверить возможности браузера и конкретного устройства |

Размеры относятся к обычным неквантованным весам из документации `whisper.cpp`; установка движка, рабочая память и временные аудиобуферы потребуют дополнительного места. Модели должны быть многоязычными для русской речи; варианты `.en` не подходят. Наличие компьютера само по себе не гарантирует достаточную производительность: при нехватке памяти или неудовлетворительной скорости предложить пользователю tiny. На достаточно мощном телефоне можно разрешить ручной выбор small после явного предупреждения о размере и возможном нагреве. Оба выбора требуют проверки на реальных устройствах.

Модель скачивается отдельно на каждом устройстве после явного действия пользователя. Она не синхронизируется между устройствами и не хранится в облачной базе или файловом хранилище аккаунта. В настройках показывать выбранную модель, размер, свободное место, обозначение «Русский», статус установки, результат проверки файла, действия «Загрузить», «Изменить модель» и «Удалить». Переключение модели не изменяет существующие заметки. Во время распознавания нельзя незаметно менять модель или отправлять аудио в облако.

Один интерфейс `SpeechToTextAdapter` должен работать с tiny и small. Платформенные адаптеры выбирают оптимальный доступный вычислительный путь, освобождают микрофон и память при остановке и сообщают фактический статус. Для слабых настольных компьютеров тестировать fallback на tiny; для мобильных не повышать модель автоматически. Сначала сравнить WER/CER, задержку после остановки записи, пик RAM, нагрузку CPU/GPU, нагрев и расход батареи на утверждённом корпусе русской речи. Пороговые значения и минимальные требования к устройству установить по итогам замеров. Не обещать одинаковое качество и скорость на разных ОС.

Проверяемые критерии приёмки: новый мобильный клиент предлагает tiny; новый настольный клиент предлагает small; оба скачивают правильный вес с проверкой SHA-256; выбор сохраняется только на данном устройстве; недостаток места и памяти даёт понятное сообщение; ручная смена модели и удаление работают; отсутствие модели не мешает ручному вводу; распознанный текст сохраняется локально и синхронизируется как обычный текст. Браузер получает отдельную матрицу поддержки.


**Языковое решение (утверждено):** всё приложение и голосовая диктовка в «Маяке» рассчитаны только на русский язык. Для мобильных используется многоязычная Whisper tiny, для настольных ОС — многоязычная Whisper small, но в обоих адаптерах язык распознавания принудительно установлен `ru`. Английские версии `.en` не применять. В настройках не показывать выбор языка; корпус приёмочных аудиозаписей и оценки точности готовить на русском. Поддержка иных языков потребует отдельного решения.
