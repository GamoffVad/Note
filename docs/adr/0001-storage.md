# ADR 0001 · Хранение данных

Статус: принято для прототипа · 26.09.2026

## Контекст

ТЗ (разделы 2–3) требует работы без сети, синхронизации между шестью платформами, приватного хранения файлов и отсутствия постоянных данных на диске serverless-функции.

## Решение

| Слой | Решение | Состояние в репозитории |
|---|---|---|
| Сервер | PostgreSQL, SQL-миграции в `packages/server/migrations` | Реализовано; тесты на PostgreSQL 16 |
| Провайдер БД | Supabase (по умолчанию) или Neon через Vercel Marketplace | Код и инструкция готовы (docs/supabase-setup.md); проект владельца ещё не создан |
| Web/PWA | IndexedDB, отдельная база на аккаунт (`mayak:<namespace>`) | Реализовано (`IndexedDbLocalStore`); тесты на fake-indexeddb, в реальных браузерах не проверено |
| Native | SQLite в каталоге данных приложения (Tauri 2) | **Не реализовано** — интерфейс `LocalStore` готов |
| Файлы | Приватный Vercel Blob за адаптером ObjectStore | **Не реализовано** — прототип загрузки/возобновления ждёт аккаунта |

### Модель на сервере

Все объекты пользователя адресуются парой `(owner_id, id)`. Идентификаторы создаёт клиент (нужно для работы без сети), но чужой id не находит строку другого владельца: попытка обращения даёт 404 без раскрытия существования, а создание с тем же id создаёт независимый объект в пространстве текущего пользователя. `owner_id` всегда берётся из проверенной сессии.

`deviceId` уникален глобально: чужой клиент не может зарегистрировать или использовать устройство другого аккаунта.

### Локальное хранилище

`LocalStore` — транзакция над хранилищами `notes`, `outbox`, `conflicts`, `shadows`, `meta`. Бизнес-правила синхронизации живут в `@mayak/sync` и одинаковы для всех реализаций. Ограничение IndexedDB: внутри транзакции можно ожидать только её собственные операции; любой посторонний `await` завершает транзакцию. Реализация на SQLite должна давать ту же семантику через `BEGIN IMMEDIATE … COMMIT`.

`localStorage` не используется как база (ТЗ, раздел 2). В браузере запрашивается постоянное хранилище (`requestPersistentStorage`), но браузер вправе отказать — это нужно показывать пользователю.

### Схема `mayak` (миграция 0002)

Все таблицы — в схеме `mayak`, не в `public`. В Supabase схема `public` публикуется через Data API, и таблицы в ней по умолчанию получают права ролей `anon` и `authenticated`. Данные Маяка доступны только через наш API, поэтому миграция отзывает у этих ролей права на схему `mayak` и включает RLS без политик (защита в глубину). API и мигратор работают от владельца таблиц, на которого RLS не действует. Проверено на локальном PostgreSQL с имитацией ролей Supabase: `anon` получает отказ в доступе.

Подключение к Supabase: API — transaction pooler (порт 6543, без prepared statements; запросы не задают `name`), миграции — session pooler или прямое подключение, SSL с проверкой по корневому сертификату (`DATABASE_CA_CERT`).

## Последствия

- Смена провайдера БД не меняет код: используется обычный `pg` и SQL без расширений, кроме встроенной `gen_random_uuid()` (PostgreSQL 13+).
- Для каждого аккаунта нужна отдельная локальная база; при смене аккаунта кэш прежнего не показывается.
- Шифрование локальной базы не заявляется (ТЗ, раздел 7).
