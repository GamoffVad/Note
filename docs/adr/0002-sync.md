# ADR 0002 · Синхронизация заметок

Статус: принято для прототипа · 26.09.2026

## Контекст

ТЗ, раздел 4: локальное сохранение до сети, outbox, идемпотентный push, pull по курсору без пропусков, явные конфликты без «последний по часам выигрывает», сохранность локальных правок при любых ошибках.

## Решение

Снимковая синхронизация на уровне заметки: каждая мутация несёт полный документ и признак «в корзине» (`operation: "upsert"`). Ревизия охватывает документ целиком, поэтому конкурентные правки разных задач одной заметки дают конфликт — осознанный компромисс MVP. CRDT — отдельный будущий ADR.

### Клиент (`packages/sync`)

1. **Локальная правка** — одна транзакция: запись заметки и outbox. `editNote()` разрешается только после commit, поэтому UI может показать «Сохранено на устройстве» только после него. Объединение нажатий (до 150 мс) и принудительная запись при blur/навигации — задача слоя UI.
2. **Одна запись outbox на заметку.** Пока запись не отправлялась, новые правки заменяют её снимок. Перед отправкой запись помечается `sent` в той же транзакции, где выбирается пакет (write-ahead). Отправленная запись неизменна: повтор идёт с тем же `mutationId` и тем же телом. Правки, сделанные во время отправки, уходят следующей мутацией после ack на базе подтверждённой ревизии.
3. **Push**: до 50 мутаций и не больше `MAX_PUSH_BODY_BYTES`. Документ больше 1 MiB не отправляется, запись помечается ошибкой, текст остаётся на устройстве.
4. **Ответы**: `applied` — ack; `conflict` — запись в `conflicts`, outbox очищается, локальная версия остаётся в заметке; `rejected` — постоянная ошибка записи.
5. **Pull**: страница применяется и курсор продвигается одной транзакцией. Если у заметки есть неотправленные правки, серверный снимок не перезаписывает их, а сохраняется в `shadows`. Если pull приносит изменение с `mutationId` нашей отправленной записи (ответ push был потерян), это считается подтверждением.
6. **410 CURSOR_EXPIRED** и первый запуск: все страницы `/bootstrap` собираются в памяти, затем одной транзакцией атомарно заменяют состояние. Outbox, конфликты и неотправленные правки сохраняются; чистые заметки, исчезнувшие с сервера, удаляются локально (сервер запрещает воскрешать их id).
7. **Конфликт**: «Моя версия» — новая мутация на актуальной серверной ревизии; «С другого устройства» — локальная заменяется серверной; «Сохранить обе» — локальная версия становится новой заметкой с `conflictOf`, оригинал получает серверную версию. Пока конфликт не решён, правки копятся локально и не отправляются.
8. **Повторы**: 1, 2, 4, 8 … 60 с с jitter, `Retry-After` приоритетен. 401 → «Войдите снова», 403 → остановка (отзыв устройства), 426 → «Обновите приложение»; outbox не удаляется ни в одном случае. Часы устройства влияют только на расписание повторов и подписи.
9. **Планировщик**: цикл каждые 3 с в активном приложении, 45 с после 10 тихих циклов, немедленный цикл по `trigger()` (фокус, сеть, правка). Фоновая работа мобильных ОС не обещается.

### Сервер (`packages/server`)

Одна мутация — одна транзакция:

1. `SELECT … FROM sync_heads WHERE owner_id = $1 FOR UPDATE` — сериализация записей владельца.
2. Повтор `mutationId`: тот же хэш тела (SHA-256 канонического JSON) — прежний результат; другой — `IDEMPOTENCY_MISMATCH`.
3. Проверка `baseRevision`. Несовпадение — `conflict` с серверным снимком; состояние не меняется и не запоминается (ревизия только растёт, повтор снова даст конфликт).
4. `revision + 1`, `seq = last_seq + 1`, запись `notes`, `note_versions`, `changes`, `mutations`; ответ — после COMMIT.

**Почему курсор не пропускает изменений.** `seq` выдаётся под блокировкой строки `sync_heads`, которая держится до COMMIT. Поэтому транзакция с большим `seq` не может стать видимой раньше транзакции с меньшим, и читатель, дошедший до `seq = N`, уже видит все события `≤ N`. С обычной глобальной sequence это не так: номер выдаётся до COMMIT, и порядок видимости может отличаться от порядка номеров.

Курсор непрозрачен: владелец, эпоха журнала, `seq`. Чужой курсор — 400, другая эпоха или `seq` старше `retained_from_seq` — 410. `/bootstrap` фиксирует high-water `seq` до чтения первой страницы; клиент применяет изменение, только если его ревизия больше известной.

## Проверено тестами

`packages/server/test/api.test.ts` и `packages/sync/test/e2e.test.ts` на PostgreSQL 16: A01–A09, A13, A14, A16, A17, а также правка во время отправки, ошибка локальной записи, слишком большой документ, 401/403/426, постраничный bootstrap. Сопоставление — в `docs/acceptance.md`.

## Не сделано

- Очистка журнала старше 90 дней, результатов `mutations` и корзины старше 30 дней — нужна фоновая задача (cron); сейчас двигается только `retained_from_seq` в тестах.
- Rate limiting.
- Нагрузочная проверка сериализации на владельца.
