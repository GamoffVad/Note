# ADR 0004 · Вход и сессии через Supabase Auth

Статус: принято для реализации · 26.09.2026

## Контекст

ТЗ, раздел 7: вход по email через выбранного Auth-провайдера (по умолчанию Supabase Auth), проверка issuer/audience/expiry и статуса сессии, управление устройством связано с реальной сессией, секреты только на сервере, для Web — сессия в HttpOnly cookie и CSRF-защита.

Факты о Supabase ниже взяты из исходников официальной документации в репозитории `supabase/supabase` (сайт supabase.com из среды разработки недоступен; эти файлы — источник тех же страниц). Прочитаны 26.09.2026.

## Решение

### Сервер: проверка access token по JWKS

- Ключи — из `https://<project>.supabase.co/auth/v1/.well-known/jwks.json`; алгоритмы ES256/RS256 (EdDSA принимается на будущее). Библиотека `jose`, как в примере Supabase. Источник: [jwts.mdx](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/auth/jwts.mdx), [signing-keys.mdx](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/auth/signing-keys.mdx).
- Проверяются подпись, `iss = https://<project>.supabase.co/auth/v1`, `aud = authenticated`, `exp` (допуск 30 с), `role = authenticated`, наличие `sub` и `session_id`; анонимные пользователи (`is_anonymous`) не принимаются. Поля — [jwt-fields.mdx](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/auth/jwt-fields.mdx).
- Кэш JWKS не дольше 10 минут: так кэширует сам Supabase, и документация предупреждает, что долгий кэш затрудняет отзыв ключа.
- **Общий секрет HS256 (legacy) не поддерживается.** Supabase прямо не рекомендует проверять им токены, а JWKS такие ключи не отдаёт. Проект должен использовать асимметричные signing keys (миграция описана в signing-keys.mdx и docs/supabase-setup.md).
- Недоступность JWKS — ответ 503 `SERVICE_UNAVAILABLE` с Retry-After, а не 401: сбой сети не должен выбрасывать пользователя из аккаунта.
- Пользователь приложения — `users.auth_subject = "supabase|<sub>"`; owner_id по-прежнему назначает сервер.

### Отзыв устройства и сессии

Access token Supabase остаётся действительным до истечения даже после выхода ([sessions.mdx](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/auth/sessions.mdx); комментарий к `signOut()` в auth-js). Поэтому отзыв устройства в Маяке:

1. помечает устройство `revoked_at`;
2. записывает `session_id` этого устройства в `revoked_sessions`;
3. каждый запрос проверяет, что `session_id` токена не отозван (401 `SESSION_REVOKED`).

Без шага 2 отозванный клиент мог бы зарегистрироваться под новым deviceId с тем же токеном. После нового входа (новая сессия) клиент сам создаёт новый deviceId. Сессия в самом Supabase при этом не завершается — для этого нужен секретный ключ и Admin API, это отдельная задача.

### Клиент (веб)

- `@supabase/supabase-js`, публикуемый ключ `sb_publishable_…` встраивается в сборку: документация относит его к ключам, которые безопасно раскрывать ([api-keys.mdx](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/getting-started/api-keys.mdx)). Секретный ключ в клиент не попадает.
- Вход без пароля: `signInWithOtp` → письмо; пользователь вводит код (`verifyOtp({type: "email"})`) или открывает ссылку в том же браузере (PKCE). Источник: [auth-email-passwordless.mdx](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/auth/auth-email-passwordless.mdx). Код в письме появляется, только если шаблон письма содержит `{{ .Token }}`.
- «Выйти» — `signOut({ scope: "local" })`: по умолчанию auth-js завершает сессии на всех устройствах.
- Токен для нашего API берётся из `getSession()` (библиотека сама его обновляет) и отправляется в `Authorization: Bearer`. Если пользователь сессии не совпадает с аккаунтом открытого пространства, токен не отправляется — заметки одного аккаунта не уйдут в другой.

### Отклонение от ТЗ: сессия не в HttpOnly cookie

ТЗ, раздел 7, требует HttpOnly cookie и CSRF для Web. Supabase указывает, что HttpOnly cookie неприменимы, когда приложение работает на клиентском JavaScript: браузерный код тогда не может читать и обновлять сессию ([sessions.mdx](https://github.com/supabase/supabase/blob/master/apps/docs/content/guides/auth/sessions.mdx)). Маяк — офлайн-приложение, где синхронизация идёт из браузера, поэтому:

- токены хранит auth-js в localStorage; риск — кража при XSS. Компенсация: строгая CSP (только свои скрипты и скрипт по хэшу, `connect-src` — свой API и проект Supabase), React экранирует текст, raw HTML не рендерится;
- CSRF не применим: API не использует cookie, а заголовок Authorization браузер сам не подставляет.

Альтернатива для будущего ADR: серверный посредник (BFF), который обменивает код на сессию и держит refresh token в HttpOnly cookie, а API-запросы защищает CSRF-токеном. Это усложняет офлайн-обновление сессии; решение — за владельцем.

## Последствия

- Для работы нужен проект Supabase с асимметричным ключом подписи; настройка — docs/supabase-setup.md.
- Тесты не обращаются к настоящему Supabase: токены подписываются тестовым ключом ES256 с теми же полями; браузерный тест перехватывает запросы к Auth-серверу. Совместимость с живым проектом нужно проверить после его создания.
